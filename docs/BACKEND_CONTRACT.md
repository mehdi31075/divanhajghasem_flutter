# وضعیت API روی هاست — ۲۰۲۶/۱۰/۰۷

در بازبینی ۲۰۲۶/۱۰/۰۷، API عمومی HTTP با User-Agent اندروید (Dalvik و Apache HttpClient) بدون توکن پاسخ ۲۰۰ داد: ۳۲ دسته، ۳۲۱ مطلب به ترتیب صعودی، جزئیات کامل و `[]` برای مطلب ناموجود تأیید شدند. ۴۰۳ مشاهده‌شده مربوط به درخواست پیش‌فرض Python بود؛ برای کلاینت اندروید تکرار نشد. ناسازگاری مقدار صفر در `cat_id`، `nid` و `latest_news` در کد و روی هاست اصلاح و دوباره بررسی شد. اجرای خود اپ قدیمی روی گوشی هنوز انجام نشده است.

بررسی مستقل TLS همچنان خطای `certificate has expired` داد؛ باز شدن سایت در Chrome به معنای تأیید اعتبار گواهی نیست. برای اتصال عادی Flutter تمدید/نصب گواهی معتبر لازم است؛ اعتبارسنجی TLS غیرفعال نشد.

پنل Laravel روی سایت اصلی بالا آمده؛ ورود با توکن و دریافت آمار، دسته‌ها و محتوای یک نوشته در Chrome تأیید شدند. دو جدول مستقل احراز هویت افزوده شده‌اند و جدول‌های اصلی دست‌نخورده‌اند. آزمون ایجاد، ویرایش و حذف محتوای زنده و اجرای کلاینت Android قدیمی انجام نشده است. بخش‌های زیر که می‌گویند نصب روی هاست انجام نشده، وضعیت پیش از این بررسی را شرح می‌دهند.

# دیتابیس بک‌اند — ۲۰۲۶/۱۰/۰۷

بک‌اند به MariaDB موجود `divanhaj_db` روی همان هاست، از طریق اتصال MySQL در Laravel، تنظیم شده است. SQLite فقط در Flutter برای کش و پیش‌نویس استفاده می‌شود. جدول‌های اصلی موجود تغییر نمی‌کنند؛ migration فقط جدول‌های مفقود را می‌سازد. ستون `news_description` از نوع `LONGTEXT` است و API حداکثر ۵٬۰۰۰٬۰۰۰ بایت برای بدنه می‌پذیرد. قرارداد خواندن بدون توکن اپ قدیمی تغییری نکرده است. اتصال واقعی روی هاست هنوز آزموده نشده.

# مهاجرت به Laravel — ۲۰۲۶/۱۰/۰۷

بک‌اند `backend/` اکنون Laravel 13 با پنل فارسی و واکنش‌گراست. URL عمومی `api.php` و قرارداد JSON اپ Android قدیمی بدون توکن حفظ شده‌اند؛ خود فایل PHP قدیمی جای خود را به route لاراول داده است. پنل و Flutter با قرارداد `mobile-api.php?action=...` و توکن Bearer کار می‌کنند. رمزهای فعلی معتبرند؛ تغییر رمز از bcrypt استفاده می‌کند.

مدیریت Flutter پیش‌فرض HTTPS است؛ endpoint خواندن عمومی تغییری نکرده. راهنمای استقرار کامل در `backend/DEPLOYMENT.md` است. انتقال روی هاست هنوز انجام نشده؛ PHP 8.3+ و گواهی TLS معتبر لازم است. گواهی فعلی سایت در بررسی امروز منقضی بود. فصل‌های بعدی که از فایل api.php دست‌نخورده یا PHP قدیمی می‌گویند، وضعیت تاریخی پیش از Laravel را شرح می‌دهند.

# اتصال با توکن — ۲۰۲۶/۱۰/۰۶

بک‌اند مستقل در `backend/` کنار پروژه است؛ فایل `divan.code-workspace` هر دو مخزن را در ادیتور نشان می‌دهد.

مسیر فعال ورود و نوشتن Flutter اکنون `mobile-api.php` است: login توکن Bearer می‌گیرد، me آن را تأیید می‌کند و create/update/delete با هدر Authorization ارسال می‌شوند. ورود آزمایشی و رمز هاردکد حذف شدند. توکن فقط در حافظه است و در SQLite یا browser storage ذخیره نمی‌شود؛ بستن کامل اپ به ورود دوباره برای مدیریت نیاز دارد.

این تغییر هنوز روی هاست deploy نشده است. راهنمای نصب و migration در `backend/README.md` است؛ تا نصب API جدید، ورود با توکن پیام «API نصب نشده» نشان می‌دهد. خواندن عمومی پیش‌فرض از `api.php` فعلی ادامه دارد. پس از نصب، برای خواندن با CORS استاندارد نیز `DIVAN_API_URL` را به `https://divanhajghasem.ir/mobile-api.php` تغییر دهید. `DIVAN_TOKEN_API_URL` مسیر مستقل ورود را اختیاری تعیین می‌کند؛ پیش‌فرض کنار endpoint خواندن است.

پنل نیز اکنون با همین API توکن کار می‌کند. فرم‌های قدیمی کوکی بازنشسته شده‌اند؛ `DIVAN_USE_TOKENS=false` دیگر برای بک‌اند فعلی قابل استفاده نیست. `api.php` عمومی تغییر نکرده؛ سازگاری فقط برای اپ Android قدیمیِ صرفاً خواندنی لازم است، نه رابط یا احراز هویت پنل قبلی.

قرارداد کوکی در ادامه شرح تاریخی است و روی پنل فعلی فعال نیست. راهنمای نصب جدید و فهرست تمام فایل‌های لازم در `backend/README.md` و `backend/DEPLOYMENT_FILES.txt` است.

# قرارداد اتصال فعلی

فرم‌ها داخل Flutter هستند و رابط پنل وب باز نمی‌شود. سرور منبع مطالب منتشرشده است. دستگاه پیش‌نویس‌های ارسال‌نشده و کش مطالعهٔ آفلاین را نگه می‌دارد؛ هیچ proxy یا بک‌اند محلی نداریم.

مطالعه برای همه آزاد است. اپ هنگام باز کردن دسته‌ها و مطالب، نسخهٔ API را می‌خواند و کش موجود را تا رسیدن پاسخ نشان می‌دهد. ابزارهای ایجاد، ویرایش و حذف پس از پنج لمس نسخهٔ برنامه در تنظیمات و ورود موفق با همان حساب پنل ظاهر می‌شوند. پیش‌نویس‌های ارسال‌نشده از تنظیمات ادمین قابل باز کردن‌اند. خروج از مدیریت نشست PHP را پایان می‌دهد و ابزارهای مدیریت را پنهان می‌کند.

## خواندن

- `GET http://divanhajghasem.ir/api.php`: دسته‌ها
- `GET api.php?cat_id=61`: مطالب کامل دسته
- `GET api.php?nid=117`: جزئیات مطلب
- پاسخ: `{"AndroidEbookApp": [...]}` یا `[]` برای نبود رکورد.
- `news_date` عنوان فرعی است؛ `news_description` بدنهٔ HTML.

## نوشتن با PHP موجود

فایل پیوست endpoint JSON برای CRUD ندارد. اپ همان قرارداد HTTP فرم‌های PHP را مستقیم مصرف می‌کند:

- ورود: `POST index.php` با `username`, `password`, `btnLogin=1` و نشست PHP.
- ایجاد: `POST add-menu.php` با `news_heading`, `news_date`, `cid`, `news_description`, `btnAdd=1`.
- ویرایش: `POST edit-menu.php?id=<nid>` با همان چهار فیلد و `btnEdit=1`.
- حذف: `POST delete-menu.php?id=<nid>` با `btnDelete=1`؛ حذف دائمی است و پیش از درخواست در اپ توضیح و تأیید دارد.

هر چهار فیلد مطلب الزامی‌اند. رمز در کد یا SQLite نگهداری نمی‌شود. نشست در موبایل در حافظهٔ کلاینت و در وب تحت مدیریت مرورگر است. پیش از هر mutation جدید، فرم با GET احراز هویت می‌شود؛ redirect یا فرم ورود مانع POST است. وجود فرم در بدنهٔ redirect، مجوز ارسال محسوب نمی‌شود.

## تأیید و پایداری

پیام HTML موفقیت PHP مبنا نیست؛ به‌علت استفادهٔ نادرست از `store_result` ممکن است اشتباه باشد. ثبت ایجاد/ویرایش با خواندن دوبارهٔ دسته و مقایسهٔ کامل محتوا تأیید می‌شود. برای ایجاد، فهرست شناسه‌های قبل از ارسال ثبت می‌شود. حذف فقط با پاسخ معتبر خالی جزئیات تأیید می‌شود.

عملیات پیش از POST در `post_operations` ثبت می‌شود. بعد از timeout یا قطع اینترنت، تلاش مجدد فقط نتیجه را با GET بررسی می‌کند؛ حتی پس از بازگشایی اپ POST تکرار نمی‌شود. اگر تطبیق یکتا ممکن نباشد، نتیجه نامشخص می‌ماند و نیازمند بررسی دستی است. سرور شناسهٔ idempotency ندارد و نتیجهٔ نامشخص را نمی‌توان همیشه خودکار حل کرد.

تأیید درخواست، به‌روزرسانی کش و حذف پیش‌نویس همان revision در یک تراکنش است. ویرایش جدیدتر باقی می‌ماند و شناسه/نسخهٔ پایهٔ سرور به آن متصل می‌شود تا ارسال بعدی ایجاد تکراری نباشد. تغییرات هم‌زمان سرور پیش از ارسال بررسی می‌شوند؛ PHP کنترل تعارض اتمیک ندارد و رقابت بعد از این بررسی همچنان محدودیت است.

عنوان، زیرعنوان و تغییر دسته HTML اصلی را حفظ می‌کنند. ویرایش بدنه با Flutter Quill انجام می‌شود؛ پیش‌نویس هم HTML و هم Delta JSON را نگه می‌دارد. هنگام ارسال، HTML در همان `news_description` قرار می‌گیرد. HTML قدیمی تا اولین تغییر واقعی متن دقیقاً حفظ می‌شود؛ تبدیل قالب‌های پیچیده به Quill با تأیید کاربر انجام می‌شود و نسخهٔ قبلی باقی می‌ماند. مسیرهای نسبی تصاویر و پیوندها پیش از تبدیل نسبت به API کامل می‌شوند.

SQLite نسخهٔ ۶ ستون `rich_text_delta` را برای بازیابی دقیق قالب پیش‌نویس اضافه می‌کند. جدول آزمایشی `local_posts` استفاده نمی‌شود و دادهٔ آن خودکار منتشر یا پاک نمی‌شود.

تاریخ نوشته: مدل و صفحهٔ مطالعه از فیلدهای اختیاری `created_at` و `updated_at` به شکل ISO 8601 با منطقهٔ زمانی پشتیبانی می‌کنند و آن‌ها را در کش هم حفظ می‌کنند. پاسخ زندهٔ فعلی هیچ‌یک را ندارد؛ `news_date` عنوان فرعی است. در نبود تاریخ، «ثبت نشده» نمایش داده می‌شود؛ زمان دریافت یا زمان ذخیرهٔ پیش‌نویس جای تاریخ واقعی سرور استفاده نمی‌شود. ثبت تاریخ‌های واقعی در PHP/پایگاه داده و انتشار آن روی سرور هنوز انجام نشده است.

## وب

درخواست‌ها مستقیم به سایت می‌روند. CORS و کوکی نشست وابسته به پیکربندی سرور و مرورگرند. `--disable-web-security` صرفاً پیش‌نمایش توسعه است و تضمین رفع محدودیت کوکی‌های cross-site نیست. برای انتشار وب، میزبانی هم‌مبدأ یا پیکربندی درست CORS و کوکی لازم است؛ اتصال موبایل محدودیت CORS مرورگر را ندارد.

بررسی زندهٔ ۲۰۲۶/۱۰/۰۶: پاسخ `index.php` هدر CORS ندارد و `PHPSESSID` را فقط با `Path=/` می‌فرستد؛ `SameSite=None; Secure` ندارد. بنابراین نشست پنل در درخواست‌های cross-site از پیش‌نمایش `localhost` در Chrome ارسال نمی‌شود. گزینهٔ `--disable-web-security` این محدودیت کوکی را حل نمی‌کند. درخواست HTTPS به همین میزبان نیز در زمان بررسی timeout شد. برای ورود وب باید اپ هم‌مبدأ با پنل میزبانی شود، یا سرور با HTTPS و تنظیم درست CORS و کوکی اصلاح شود. ورود Android از کلاینت غیرمرورگری استفاده می‌کند و به این تنظیم CORS/کوکی cross-site وابسته نیست.
